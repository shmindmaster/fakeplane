## Negative control

Every case is also run against an empty output, which must fail it. This catches a checker that passes everything. It does not show that each individual check works: a case fails when any one of its checks does.

## Methodology

- **Completion vs success.** Run completion is the share of cases where the target returned an output without error; task success is the share where it completed *and* every check passed. A run can complete and still fail, so the two are reported separately and the gate requires both.
- **Why benchmark a stub.** The stub echoes the prompt, so these numbers say nothing about model quality. They pin the harness itself: the same suites must give the same verdicts every run. A changed check, a parser change or an edited golden set shows up here as a moved number or a determinism failure before it can distort a real model comparison. That makes this a regression test for the harness.
- **Determinism.** Each suite runs 3 times in one process. Outputs are the raw target responses; verdicts are the per-case records with wall time removed; both are compared by SHA-256.
- **Throughput** is cases divided by wall time for `evaluate_suite`, with no network calls. It measures harness overhead, varies by machine, and is the only figure expected to change between runs.
